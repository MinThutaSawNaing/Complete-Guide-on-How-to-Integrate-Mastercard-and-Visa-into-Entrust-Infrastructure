1. Purpose and Scope

This document describes the procedure for preparing and configuring the Entrust software stack so that a bank can issue Mastercard or Visa card products. The work is primarily a key ceremony: the correct keys must be created in the correct token table with the correct attributes, and the correct certificates must be imported in the correct sequence.

The complete procedure is summarised below:

Create token tables  ->  Generate issuer key pair  ->  Build CA request (ZIP)
     ->  Bank submits request to Mastercard  ->  Issuer certificate (.cEF) returned
     ->  Import CA certificate (.hep + .sep)  ->  Import issuer certificate (.cEF)
     ->  Import request/session keys (2DES, two components)
     ->  Import EMV profile and PQDF tool files  ->  Ready for issuance

Approximately 50 per cent of the integration effort is complete once the CA certificate and the issuer certificate have been imported successfully. The remaining work consists of importing the operational keys and the EMV profile files.

2. Prerequisites

2.1 Entrust portals used

All three portals of the Entrust ecosystem are used in this procedure.

No.PortalRole in this procedure
1Key Manager PortalToken tables, key pairs, certification authority requests, certificate and key imports
2EMV Profile Manager PortalEMV kernel and profile configuration for the card applet
3Card Wizard PortalCard personalization workflow and PQDF tool-file generation

2.2 Conditions to confirm with the client before starting

  • The client operates separate token tables for testing (UAT) and production (live); refer to section 3.1.
  • The bank's BIN number is available. The BIN is used as the key owner.
  • A bank HOST operator is available to generate 2DES keys with two key components.
  • Access to the Mastercard portal is available in order to download the .hep and .sep files.

3. Procedure

3.1 Create separate token tables

Some clients store all key material in a single token table. This is workable but not advisable, because test and production material are then held in the same container. Two separate token tables must be created: one for testing (UAT) and one for production (live).

Create a new token table from the Key Manager Portal:

Entrust Key Manager Portal
  Setup
    HSM Configurations
      Right-click the HSM  ->  Login
        Create a new token table  ->  Assign a name

The token table is created once it appears in the HSM tree.

3.2 Generate the issuer key pair (Issuer_PK / Issuer_SK)

This step creates the Issuer Public Key (Issuer_PK), which is used to build the certification authority request, and the matching Issuer Private Key (Issuer_SK).

Critical. This is the most error-prone step of the entire integration; approximately 80 per cent of certification authority requests fail because of incorrect parameters at this point. Verify every attribute before generating the keys.

Navigate as follows and apply the parameters in the table below:

Key Manager Portal
  Home
    Select the correct token table  ->  Login
      Log in as Security Officer (SO)
        Generate Key Pair (side bar)  ->  Apply the parameters below
ParameterValueComment
Key typeAny RSA-based key typeNaming depends on the HSM key-type set
Key length1976 bitsAs specified for Mastercard in this procedure
OwnerThe bank's BIN numberBinds the key material to the issuer identity
Version06 = live, EF = UATThe version field identifies the environment
UsagesEncrypt, Wrap, VerifyAll three usages are required
AttributesExtractable, Exportable, DeletableAll three attributes are required
Exponent03Standard RSA public exponent
Note. Issuer_PK and Issuer_SK are generated with an identical procedure and identical parameters; only the key name differs.

3.3 Generate and submit the certification authority request

Generate the certification authority request that will be submitted to Mastercard:

Key Manager Portal
  Certificates
    Request a Certificate
      Mastercard
        Select the Issuer Public Key created in section 3.2
          Generate Request Certificate  ->  (ZIP file)

The request is transferred as follows:

  1. Entrust generates the request as a ZIP archive.
  2. The ZIP archive is handed to the bank, which submits it to Mastercard.
  3. Mastercard returns the issuer certificate as a .cEF file.
Important. The .cEF file on its own is not sufficient to go live with Mastercard. Two further files must also be obtained; both are downloaded from the Mastercard portal. This is a common misunderstanding at banks.
ArtifactFormatSourcePurpose
Issuer certificate.cEFMastercard reply to the CA requestImported as the issuer certificate (section 3.4)
Hardware encryption program.hepDownload from the Mastercard portalUsed to build the CA certificate in Entrust (section 3.4)
Security program.sepDownload from the Mastercard portalUsed to build the CA certificate in Entrust (section 3.4)

All three files are required: .cEF, .hep, and .sep.

3.4 Import the CA certificate and the issuer certificate

Once all three files have been received, import them into Entrust in the following order.

Step 1 — CA certificate (HEP and SEP)

Key Manager Portal
  Import Certificate
    CA Certificate
      Select both the .hep and the .sep file  ->  Import

Step 2 — Issuer certificate

Key Manager Portal
  Import Certificate
    Issuer Certificate
      Select the .cEF file  ->  Import
Note. Once both imports have completed successfully, approximately 50 per cent of the integration is finished.

3.5 Import the required keys into the token table

The next stage is to request and import the operational keys (request and session keys) into the token table. Entrust reports which keys are required; this list is passed to the bank, which generates the keys with its HOST.

Critical. Instruct the bank to generate 2DES keys with two components. Entrust requires at least two key components in order to import a key.

When the key components have been received, import them as follows:

Key Manager Portal
  Import Secret Key or Key Pair
    Import Key with Components
      Enter the plain key components
        Enter the components a second time  ->  Generate Key

3.6 Import the EMV profile and PQDF tool files

Once the keys are in place, Entrust provides the following deliverables:

DeliverablePurpose
EMV profile fileConfiguration of the card applet and kernel
PQDF tool filesPersonalization data tool files used for card issuance

Both are imported by following the guidelines supplied with the files.

Note. Minor adjustments to the configuration files are normally required to match the customer's card design and applet requirements before the first production run.

4. Verification Checklist

The integration may be signed off only when every item below has been confirmed.

  • Two token tables exist: one for UAT and one for production.
  • Issuer_PK and Issuer_SK were generated with the correct BIN owner, version (06 / EF), usages, attributes, and exponent 03.
  • The CA request ZIP file was generated and handed to the bank.
  • The bank submitted the request and Mastercard returned the issuer certificate (.cEF).
  • The .hep and .sep files were downloaded from the Mastercard portal.
  • The CA certificate was imported (both .hep and .sep).
  • The issuer certificate was imported (.cEF).
  • The required keys were requested from the bank as 2DES keys with two components each.
  • The keys were imported using Import Key with Components (components entered twice).
  • The EMV profile was imported.
  • The PQDF tool files were imported and tuned for the customer's cards.

5. Known Failure Modes and Mitigations

No.Failure modeConsequenceMitigation
1Incorrect key-pair parameters (usages, attributes, exponent, or version)Approximately 80 per cent of CA request failures originate hereRe-verify the parameter table in section 3.2 before generating the keys
2Only the .cEF file is obtainedThe integration stalls at personalizationObtain all three files: .cEF, .hep, and .sep
3A single token table is shared by UAT and productionOperationally impractical; test material is exposed to production processesAlways create separate token tables (section 3.1)
4The bank generates keys with a single componentEntrust cannot import the keyInstruct the bank to generate 2DES keys with two components
5EMV or PQDF files are imported without tuningCards behave incorrectly for the specific customer designFollow the vendor guidelines and tune the files per customer card
